## P0 - security / correctness

- [x] **P0-1 (HIGH / S) - DID provisioning used a throwaway key.** `tenant/routes/did.route.ts` minted an inline ES256 keypair, discarded the private half, and published a verification method whose `type` (`JsonWebKey2020`) did not match its key field (`publicKeyMultibase`) - so any VC issued after provisioning failed verification. **DONE:** the route now delegates to `provision-tenant-did.flow.ts` (reuses the tenant's real ACTIVE `TenantSigningKey`, publishes `publicKeyJwk`). Test rewritten to the flow-mock route-contract pattern; new case asserts flow delegation + 409 mapping. `did.route.test.ts` 4/4 green.
- [x] **P0-2 (HIGH / S) - unguarded provider fetches in social login.** Google/GitHub/Microsoft profile fetches used raw `fetch(...).json()` with no `resp.ok` check, so an error payload parsed straight into the identity upsert (`providerUserId: undefined` / wrong email). **DONE:** added `fetchProviderJson()` (non-2xx, malformed JSON, and network failures all raise `ApiError(..., 502, "SOCIAL_PROVIDER_ERROR")`; provider detail is logged, not returned). Used at all 3 call sites.
- [x] **P0-3 (MED / M) - revocation side effects were fire-and-forget.** The durable `RevokedJti` write was `void ... .catch(() => {})`, so a failed DB write was silently discarded and revocation could survive only in Redis' single-process in-memory fallback. **DONE:** new `src/lib/security/revoke-access-token.ts` pairs both tiers - `blocklistAccessToken()` awaits an idempotent `revokedJti.upsert` (TTL derived from the token's own `expiresAt`) then logs (never swallows) Redis failures; `blockJtiBestEffort()` is the Redis-only variant. Applied in `token-revoke.flow.ts`, `revoke-token-by-id.flow.ts`, `token-refresh.flow.ts` (`blocklistLiveAccessTokens`), `identity/routes/profile.route.ts`, `auth/routes/session.route.ts`. oauth flows + session route: 51/51 green.
