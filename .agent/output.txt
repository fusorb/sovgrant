## P0 - security / correctness

- [x] **P0-1 (HIGH / S) - DID provisioning used a throwaway key.** `tenant/routes/did.route.ts` minted an inline ES256 keypair, discarded the private half, and published a verification method whose `type` (`JsonWebKey2020`) did not match its key field (`publicKeyMultibase`) - so any VC issued after provisioning failed verification. **DONE:** the route now delegates to `provision-tenant-did.flow.ts` (reuses the tenant's real ACTIVE `TenantSigningKey`, publishes `publicKeyJwk`). Test rewritten to the flow-mock route-contract pattern; new case asserts flow delegation + 409 mapping. `did.route.test.ts` 4/4 green.
- [x] **P0-2 (HIGH / S) - unguarded provider fetches in social login.** Google/GitHub/Microsoft profile fetches used raw `fetch(...).json()` with no `resp.ok` check, so an error payload parsed straight into the identity upsert (`providerUserId: undefined` / wrong email). **DONE:** added `fetchProviderJson()` (non-2xx, malformed JSON, and network failures all raise `ApiError(..., 502, "SOCIAL_PROVIDER_ERROR")`; provider detail is logged, not returned). Used at all 3 call sites.
- [x] **P0-3 (MED / M) - revocation side effects were fire-and-forget.** The durable `RevokedJti` write was `void ... .catch(() => {})`, so a failed DB write was silently discarded and revocation could survive only in Redis' single-process in-memory fallback. **DONE:** new `src/lib/security/revoke-access-token.ts` pairs both tiers - `blocklistAccessToken()` awaits an idempotent `revokedJti.upsert` (TTL derived from the token's own `expiresAt`) then logs (never swallows) Redis failures; `blockJtiBestEffort()` is the Redis-only variant. Applied in `token-revoke.flow.ts`, `revoke-token-by-id.flow.ts`, `token-refresh.flow.ts` (`blocklistLiveAccessTokens`), `identity/routes/profile.route.ts`, `auth/routes/session.route.ts`. oauth flows + session route: 51/51 green.
- [x] **P0-4 (HIGH / M) - the session could not be recovered after a page reload. RESOLVED (2026-11-11).** Two published behaviours compounded, and neither could be worked around from inside the provider tree:
  1. `facet-auth`'s `SgProvider` mount effect does `const token = storage.getAccessToken(); if (!token) { setState(signed-out); return; }` - it only attempts the refresh-cookie exchange when storage **already** holds an access token (`facet-auth/dist/index.js:84-89`).
  2. `facet-sdk`'s `SgClient.request` only calls `onTokenRefresh` when `this.accessToken` is truthy (`facet-sdk/dist/index.js:111`).
  Our `zustandTokenStorage` deliberately persists no tokens, so after a reload `getAccessToken()` was `""`, SgProvider short-circuited to signed-out, no refresh was ever attempted, and every later call 401'd while `src/app/page.tsx` still redirected into a console shell that could never load data. `SessionBootstrap`'s tenant hydration also raced a token that never arrived.
  **FIX - option (a), which keeps tokens out of localStorage:** new `src/providers/auth-bootstrap.tsx` mounts **above** `SgProvider`. It performs the refresh-cookie exchange once before the provider mounts and seeds the store, so `SgProvider` comes up holding a real token and takes its normal `me()` restore path. A 401/403 clears the stale persisted marker; a network error (statusCode 0) leaves it alone rather than discarding the user's session on a blip. `SessionBootstrap` was reworked to stop hand-restoring the user from localStorage and to mirror facet-auth's *resolved* session instead - releasing `isLoading` and hydrating tenants only once a token exists.
  **Cost:** one blank frame while the exchange settles (unavoidable without introducing a hydration mismatch). **Compatibility:** stays correct even if facet-auth later learns to self-refresh - `SgProvider` only refreshes when its storage is empty, so it would find the seeded token and call `me()` rather than refreshing twice.
- [x] **P0-7 (HIGH / M) - the httpOnly refresh cookie was never stored or sent, so the whole refresh path was inert. RESOLVED (2026-11-11).** Found while establishing the prerequisites for P0-4. `client.ts` in facet-sdk never sets a `credentials` option, and `src/sdk/index.ts` passed no `fetchInit`, so fetch fell back to its default `credentials: "same-origin"` - while the app calls the API **cross-origin** (`NEXT_PUBLIC_API_URL=http://localhost:4000/api/v1`, app on :3000). A cross-origin response's `Set-Cookie` is therefore ignored by the browser: the cookie set at login was never stored, so `auth.refresh("")` always failed with `400 refresh token required` and the access token simply expired after its TTL (15m) with no way to renew. The `next.config.ts` rewrite to `/api/:path*` never applied, because the SDK points at the absolute backend URL.
  **FIX:** one line - `fetchInit: { credentials: "include" }` on the SgClient in `src/sdk/index.ts`. The backend was already correct (`build-server.ts` registers cors with `credentials: true` against `ALLOWED_ORIGINS`), and `fetchInit` is public config in the published 2.1.1, so this needed no upstream release. Fixed locally rather than waiting on a package publish; still correct if upstream later defaults it. **Note:** this is also why "log in, use the console, reload" behaved the way it did - it was two independent defects (P0-4 and P0-7), and fixing only one would not have worked.
- [x] **P0-5 (HIGH / L) - the migration chain had drifted from `schema.prisma`, so the backend was not actually functional against Postgres.** Found 2026-11-11 while landing P1-3, by diffing the live DB against the schema (`prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`). Three gaps, **all invisible to `pnpm test` because the suite mocks the database**:
  1. **`PairedDevice` and `DeviceApproval` were never migrated.** Both are declared in `schema.prisma`, but no migration creates either (verified: no `CREATE TABLE` for them anywhere in `prisma/migrations`). Seven flows use them - `register`/`list`/`revoke-paired-device` and `create`/`poll`/`approve`/`reject-device-approval` - so device pairing and device approvals failed at runtime.
  2. **`20260822000000_remove_dead_audit_enum_values` deleted three LIVE enum values.** Postgres cannot `DROP VALUE` from an enum, so that migration recreated `AuditLogAction` from a **hand-copied list** that omitted `PASSKEY_USED`, `CREDENTIAL_ISSUED` and `CREDENTIAL_REVOKED`, while the schema kept declaring them. Writers: `issue-credential.flow.ts` (audit **and** webhook event type), `revoke-credential.flow.ts`, `passkey-authenticate.flow.ts`. Each would fail with `invalid input value for enum`, so **credential issuance and revocation were broken against a real database**.
  3. `ApiKey` and `ExternalIdentifier` columns did not match the schema (timestamp precision, a missing default drop, the `ApiKey.keyHash` index and both `ApiKey` foreign keys).
  **FIX:** `20261111000010_repair_schema_drift`, generated with `prisma migrate diff --from-migrations prisma/migrations --to-schema prisma/schema.prisma --script` - produced from the chain itself rather than hand-written. Verified: that diff now returns only Prisma's `-- This is an empty migration.` placeholder = **zero drift**.
  **PROCESS GAP (the actual lesson):** the Tier-2 check that catches exactly this - `prisma/migrations/rollback.test.ts` - was opt-in behind `ARC_ID_ROLLBACK_TEST=1` and needs a shadow DB, so it never ran. Worse, **three separate defects made it unable to run or unable to fail**, all now fixed:
  1. Its DB probe used a 3s connect timeout; on this box the probe timed out, so both Tier-2 checks hit `if (!reachable) return;` and an **opted-in run went green having verified nothing**. Now 15s, and `beforeAll` asserts reachability, so opting in can no longer silently do nothing.
  2. It asserted `diff.trim() === ""`, but Prisma 7 renders a zero-drift diff as the placeholder comment `-- This is an empty migration.` (31 bytes). It now accepts either form.
  3. It shelled out via `npx prisma ...`, which resolves through the network and hangs here. It now calls the installed CLI entry point directly, and renders the diff with `-o <tmpfile>` because `--script` piped to stdout hangs on Windows.
  **Verified with the guard repaired:** `migration chain reproduces schema.prisma with zero drift` (15.1s) and `migrate deploy ... status up to date` (8.6s) both genuinely run and pass, 5/5. **ACTION TAKEN (2026-11-11):** `ci.yml` now sets `ARC_ID_ROLLBACK_TEST: "1"` on the rollback-guard step, and creates the shadow database first via `scripts/create-shadow-db.mjs` (the Postgres service container only creates `DATABASE_URL`'s database, and `migrate diff --from-migrations` refuses to create one itself). Before this, that step ran **Tier 1 only** - green on every push while checking nothing about drift, which is precisely why this went unnoticed for so long. The helper mirrors `prisma.config.ts`'s shadow resolution, is idempotent, and was verified locally (create, re-run no-op, guard 5/5 with the flag). And never hand-copy an enum's value list - diff it.
  **STATE: RESOLVED and applied.** Both migrations are committed **and applied** to the local `sg` database (37 rows in `_prisma_migrations`, none unfinished): `AccessDelegation` is gone, `PairedDevice`/`DeviceApproval` exist, `AuditLogAction` is back to 53 values. **Note for next time:** a bare `prisma migrate deploy` **hangs** in this environment (it loads the config and then never opens a DB session), while `pnpm prisma:deploy` - which passes `--schema=prisma/schema.prisma` explicitly - completes normally. Two additive side effects: an empty `sg_shadow` database was created so the Tier-2 drift check can run, and a pre-migration `pg_dump` of `sg` sits in the session scratchpad.
- [x] **P0-6 (HIGH / S) - access tokens could not be verified via JWKS (blocked Relnex). RESOLVED (2026-11-11).** From `.agent/todo.txt`. The root cause was two halves of one gap: `signJwt` set only `{ alg }` in the protected header, and `GET /oauth/jwks` published only the ACTIVE `TenantSigningKey` rows (tenant VC/DID **EC** keys) - never the **RSA** key that actually signs access tokens. A relying party fetching the advertised `jwks_uri` therefore had neither the key nor a `kid` to select it.
  **Fix:**
  1. New `src/lib/jwt/jwks.ts` owns key identity. The `kid` is the **RFC 7638 JWK thumbprint** of the configured RSA **public** key, so it is a stable function of the key material (survives restarts, changes automatically on rotation) and is identical on the token and the published JWK by construction. It works from the public key alone - the signing key is deliberately **not** imported as extractable just to compute an id.
  2. `signJwt` takes an optional `kid` and emits it in the protected header; `TokenService.issue` derives it (memoised per PEM in `jwks.ts`) and passes it on the RS256 path only. HS256 tokens carry no `kid` - there is no JWKS for them to name.
  3. `GET /oauth/jwks` now publishes that RSA key first, alongside the tenant keys. `openid-configuration.jwks_uri` already pointed at this endpoint, so discovery needed no change.
  **Verified against the real `certs/` pair** - prototyped before the change landed, then encoded as `src/modules/oauth/routes/jwks.route.test.ts` (6 tests): the published set verifies a token minted by the signing path (`createLocalJWKSet` is the offline equivalent of `createRemoteJWKSet` on a fetched document), the token's `kid` equals the published JWK's `kid`, a token signed by a different key is rejected (`ERR_JWS_SIGNATURE_VERIFICATION_FAILED`), tenant keys still publish, and a symmetric deployment publishes no RSA key.
   **For Relnex:** set `SG_JWKS_URL` and drop the pinned `SG_JWT_PUBLIC_KEY` fallback.
- [x] **P0-8 (HIGH / M) - token-type confusion: an ID token was accepted as a bearer access token. FIXED (2026-11-13).** The access token and the ID token are signed with the same key, and the ID token carries `sub` + `jti`, so `req.jwtVerify()` accepted it and the guard never asked what kind of token it was. An ID token (1h TTL, and NOT covered by the logout/revocation paths, which block access-token JTIs) therefore acted as an access token - with a longer lifetime than the access token itself. **FIX:** `TokenService.issue` stamps `token_use: "access"` / `"id"` (typed in `src/lib/jwt/types.ts`), and the guard rejects anything that is not `"access"` - including unmarked tokens. Access tokens minted before the deploy 401 once and are refreshed by the SDK. `src/api/plugins/auth-guard.plugin.test.ts` (5 tests: access accepted, ID rejected, unmarked rejected, revoked jti rejected, foreign key rejected). No route test caught this because route tests mock `fastify.auth` wholesale.
- [x] **P0-9 (HIGH / M) - the rate limiter trusted unverified JWT claims, so every limit was bypassable. FIXED (2026-11-13).** `keyGenerator` base64-decoded the Bearer token and bucketed by the raw `sub` without verifying the signature. Any caller could send `Bearer x.<base64 {"sub": random}>.y` and mint a fresh bucket per request - defeating the global limit and every per-route limit, including login (10/min), magic-link (3/15min) and password reset (5/15min). **FIX:** the keyGenerator now verifies with `fastify.jwt.verify` (same config as the guard) and falls back to IP keying on any failure. **Second defect found while fixing this:** the plugin THROWS `errorResponseBuilder`'s return value, and ours returned a plain object the error handler could not classify - so every rate-limit rejection surfaced as a **500** (plus an "unhandled runtime failure" log), not a 429. It now returns `ApiError.tooManyRequests`. `src/api/plugins/rate-limit.plugin.test.ts` (3 tests).
- [x] **P0-10 (MED / S) - `/oauth/introspect` did not authenticate its caller, and 500'd on live tokens. FIXED (2026-11-13).** RFC 7662 §2.1 requires caller authentication; the route only checked that an `Authorization: Basic` header *existed* and never verified it, so any caller could introspect any token string and read its metadata. **FIX:** Basic credentials are decoded and verified against the Client row's argon2 `clientSecret`; public clients and bad credentials are 401, never a silent `active:false` oracle. **Second defect:** the live-token branch returned `aud` as the stored JSON array against a `z.string()` response schema, so introspection of any live token with an audience **500'd** - now space-delimited per RFC 7662. `src/modules/oauth/routes/introspect.route.test.ts` (7 tests).

- [x] **P1-3 (HIGH / M) - `identity/delegations` returned 501 behind a reachable, always-broken page.** **RESOLVED - storage dropped, surface removed, feature deferred.** `AccessDelegation` was dead schema: nothing read or wrote it (its only reference was the tenant-isolation allow-list), it had no link to `Client`, and its `DELEGATION_*` audit enums had already been deleted in `20260822000000`. When the feature is designed, add the SDK methods together with the enforcement.
- [x] **P1-4 (HIGH / M) - SDK<->API contract drift.** **RESOLVED upstream in `@fusorb/facet-sdk` 4.0.0; the three local adapters are deleted (2026-11-13).** For the record, the drift they covered was:
  - **external ids (was genuinely failing):** POST body corrected to `{ type, value, displayValue? }` (the SDK sent `{ provider, externalId }`, which the route's zod rejects), and the response is typed `{ id, type, displayValue, verified, createdAt }` rather than `{ id, provider, externalId, linkedAt }`. Added the two endpoints the SDK never had - `requestVerification` / `confirmVerification` (`POST /identity/external-ids/:id/verify|confirm`).
  - **devices:** response corrected to `{ id, platform, browser, createdAt, lastSeenAt }`; the SDK advertised `name`/`lastUsedAt`, which the API never returns.
  - **policy:** `TenantPolicyUpdate` carries the six fields the route actually accepts (zod was silently stripping `passwordRules`/`loginMethods`, so those updates vanished with no error), and `get` is typed `| null` because the route returns `data: policy ?? null`.
  **Upstream status (verified 2026-11-13 against the published 4.0.0 `dist`, not a changelog):** all of it is fixed - `linkExternalId` sends `{ type, value, displayValue? }`, `confirmExternalId` posts `{ code }` and returns `{ id, verified }`, `verifyExternalId` returns `{ success, type }`, `getPolicy` is `TenantPolicy | null`, `Device` matches `presentDevice()`, `TenantPolicy` is the six accepted fields, and the delegation methods are gone (that half of P1-3). So `externalIds` / `devices` / `policies` were deleted from `src/sdk/index.ts` and the three hooks call `IdentitySdk` / `TenantSdk` directly. `ExternalIdType` stays - the SDK types the identifier type as a plain `string` while the route accepts exactly six values. The `apiKeys` adapter stays too: upstream still ships no `ApiKeySdk` (P1-2). **The old "do not delete on a version bump" rule earned its keep:** 3.0.0 was published first and was still wrong in two places, so deleting then would have shipped a confirm that 400s and a `getPolicy` that lies about `null`. Re-checking the published artifact first is what caught it.
