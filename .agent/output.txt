## P0 - security / correctness

- [x] **P0-1 (HIGH / S) - DID provisioning used a throwaway key.** `tenant/routes/did.route.ts` minted an inline ES256 keypair, discarded the private half, and published a verification method whose `type` (`JsonWebKey2020`) did not match its key field (`publicKeyMultibase`) - so any VC issued after provisioning failed verification. **DONE:** the route now delegates to `provision-tenant-did.flow.ts` (reuses the tenant's real ACTIVE `TenantSigningKey`, publishes `publicKeyJwk`). Test rewritten to the flow-mock route-contract pattern; new case asserts flow delegation + 409 mapping. `did.route.test.ts` 4/4 green.
- [x] **P0-2 (HIGH / S) - unguarded provider fetches in social login.** Google/GitHub/Microsoft profile fetches used raw `fetch(...).json()` with no `resp.ok` check, so an error payload parsed straight into the identity upsert (`providerUserId: undefined` / wrong email). **DONE:** added `fetchProviderJson()` (non-2xx, malformed JSON, and network failures all raise `ApiError(..., 502, "SOCIAL_PROVIDER_ERROR")`; provider detail is logged, not returned). Used at all 3 call sites.
- [x] **P0-3 (MED / M) - revocation side effects were fire-and-forget.** The durable `RevokedJti` write was `void ... .catch(() => {})`, so a failed DB write was silently discarded and revocation could survive only in Redis' single-process in-memory fallback. **DONE:** new `src/lib/security/revoke-access-token.ts` pairs both tiers - `blocklistAccessToken()` awaits an idempotent `revokedJti.upsert` (TTL derived from the token's own `expiresAt`) then logs (never swallows) Redis failures; `blockJtiBestEffort()` is the Redis-only variant. Applied in `token-revoke.flow.ts`, `revoke-token-by-id.flow.ts`, `token-refresh.flow.ts` (`blocklistLiveAccessTokens`), `identity/routes/profile.route.ts`, `auth/routes/session.route.ts`. oauth flows + session route: 51/51 green.
- [ ] **P0-4 (HIGH / M) - the session cannot be recovered after a page reload.** Found while wiring F4; **decide and fix before F5** (ordering rule: close P0 first). Two published-package behaviours compound:
  1. `facet-auth`'s `SgProvider` mount effect does `const token = storage.getAccessToken(); if (!token) { setState(signed-out); return; }` - it only attempts the refresh-cookie exchange when storage **already** holds an access token (`facet-auth/dist/index.js:84-89`).
  2. `facet-sdk`'s `SgClient.request` only calls `onTokenRefresh` when `this.accessToken` is truthy (`facet-sdk/dist/index.js:111`).
  Our `zustandTokenStorage` deliberately persists no tokens (the refresh token lives in the httpOnly cookie; `sg-session` holds the user only), so after a reload `getAccessToken()` is `""` -> SgProvider short-circuits to signed-out -> **no refresh is ever attempted** -> every later call 401s. Meanwhile `SessionBootstrap` has restored the persisted user, so `src/app/page.tsx` still redirects into a console shell that cannot load any data. Also means `SessionBootstrap`'s tenant hydration races a token that never arrives.
  **Options:** (a) exchange the refresh cookie *before* mounting `SgProvider` - a small gate that calls `auth.refresh("")`, writes the tokens into the store, then renders the provider; keeps tokens out of localStorage, costs one gate render, and needs no change to facet behaviour. (b) persist the access token and seed `storage.getAccessToken()` from it - what facet-auth's own `defaultStorage` does, but it puts a bearer token where XSS can read it. **Recommendation: (a).**

## P1 - architecture integrity

- [ ] **P1-1 (MED / L) - red fat routes holding business logic instead of flows.** Routes own DB/tx/crypto/audit inline, violating rule #1. Migrate highest-risk first: `tenant/routes/{did,signing-key,membership,policy,invite,tenant}.route.ts`, `identity/routes/{profile,admin}.route.ts`, `auth/routes/{password,session,mfa,passkey,magic-link,social}.route.ts`, `oauth/routes/{clients,tokens}.route.ts`, `webhooks/routes/webhook-config.route.ts`, `idp/routes/idp.route.ts`. Reference pattern: `credentials/*`, `audit/*`, `auth/login`.
- [ ] **P1-2 (LOW / S) - SDK<->API gap: `api-key` has no SDK class.** Backend `api-key` module (`POST /api-keys/create`, `GET /api-keys`, `DELETE /api-keys/:id`) has no `ApiKeySdk` in `@fusorb/facet-sdk`. Interim: the frontend `apiKeys` adapter uses `sgClient.get/post/del`. Request an `ApiKeySdk` upstream.
- [x] **P1-3 (HIGH / M) - `identity/delegations` returned 501 behind a reachable, always-broken page.** **RESOLVED - surface removed, feature deferred.** `AccessDelegation` exists in `prisma/schema.prisma` but is **dead schema**: no repository, flow or service reads or writes it (its only reference was the tenant-isolation allow-list). Shipping CRUD would let a caller "grant" scopes that nothing honours - worse than an honest 501 for an IAM product - so the misleading surface is gone: nav entry, stub page (`app/console/identities/delegations`) and `useDelegations` deleted. The three endpoints stay as 501 stubs with the four design questions that must be settled first recorded in `delegation.route.ts`: delegatable-scope allow-list, who may be a grantee, **the enforcement point** (no token-issuing path consults grants today, so CRUD + enforcement must land together), and revocation semantics. **To un-defer:** answer those four.
- [x] **P1-4 (HIGH / M) - SDK<->API contract drift.** **RESOLVED - local adapters.** `src/sdk/index.ts` now exposes `externalIds`, `devices` and `policies` adapters over `SgClient`, typed from the route validators, and `use-external-ids` / `use-devices` / `use-policy` call them instead of the SDK methods:
  - **external ids (was genuinely failing):** POST body corrected to `{ type, value, displayValue? }` (the SDK sent `{ provider, externalId }`, which the route's zod rejects), and the response is typed `{ id, type, displayValue, verified, createdAt }` rather than `{ id, provider, externalId, linkedAt }`. Added the two endpoints the SDK never had - `requestVerification` / `confirmVerification` (`POST /identity/external-ids/:id/verify|confirm`).
  - **devices:** response corrected to `{ id, platform, browser, createdAt, lastSeenAt }`; the SDK advertised `name`/`lastUsedAt`, which the API never returns.
  - **policy:** `TenantPolicyUpdate` carries the six fields the route actually accepts (zod was silently stripping `passwordRules`/`loginMethods`, so those updates vanished with no error), and `get` is typed `| null` because the route returns `data: policy ?? null`.
  Still worth raising upstream so the published types get corrected at source.
